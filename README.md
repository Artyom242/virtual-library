# Virtual Library

Учебный backend-проект виртуальной библиотеки на Go. Проект развивается
как система из нескольких сервисов и предназначен для практического
изучения разработки REST API, работы с PostgreSQL, межсервисного
взаимодействия, тестирования и эксплуатации backend-приложений.

> **Статус проекта:** в разработке. На текущем этапе реализуется
> `Catalog Service`; `Circulation Service` и часть инфраструктурных
> возможностей запланированы.

## Цели проекта

Virtual Library --- практический проект для разработки backend-системы
на Go. Основные цели:

-   спроектировать и реализовать несколько взаимодействующих сервисов;
-   освоить идиоматичный Go и распространённые подходы к организации
    backend-приложений;
-   реализовать REST API и межсервисное взаимодействие;
-   работать с реляционной базой данных, транзакциями и миграциями;
-   применять unit- и интеграционные тесты;
-   освоить кэширование, асинхронную обработку событий и базовые
    практики отказоустойчивости;
-   добавить наблюдаемость и подготовить приложения к запуску в
    контейнерах.

Проект ориентирован на обучение практикам, применимым в реальных
backend-системах. Инструменты добавляются по мере появления
соответствующих задач, а не только ради расширения стека.

## Функциональность

### Реализовано или находится в текущей работе

#### Catalog Service

Сервис отвечает за каталог библиотеки.

-   получение списка книг;
-   получение книги по идентификатору;
-   создание книги;
-   удаление книги;
-   разделение HTTP-обработчиков, бизнес-логики и слоя хранения;
-   in-memory реализация репозитория для разработки и тестирования;
-   подключение PostgreSQL и разработка PostgreSQL-репозитория.

Точный набор доступных HTTP-маршрутов следует смотреть в
`catalog-service/internal/httpapi/router.go`.

### Запланировано

#### Catalog Service

-   полноценный CRUD, включая обновление книги;
-   управление авторами и связями книг с авторами;
-   SQL-миграции;
-   интеграционные тесты с настоящей PostgreSQL.

#### Circulation Service

Сервис будет отвечать за операции обращения книг:

-   учёт читателей;
-   выдача книг;
-   возврат книг;
-   контроль доступности экземпляров;
-   история выдач и возвратов.

Детальная модель данных и API будут определены при проектировании
сервиса.

#### Взаимодействие и инфраструктура

-   gRPC и Protocol Buffers для синхронного межсервисного
    взаимодействия;
-   RabbitMQ для асинхронного обмена событиями;
-   Redis для кэширования;
-   структурированные логи на базе `log/slog`;
-   OpenTelemetry для распределённой трассировки;
-   Prometheus для сбора метрик;
-   Docker Compose для локального запуска инфраструктуры;
-   CI/CD и практики production-развёртывания.

## Архитектура

Репозиторий организован как монорепозиторий с отдельными Go-модулями для
сервисов.

### Планируемая логическая схема

``` text
                         Клиент
                           |
                      HTTP / REST
                           |
              +------------+------------+
              |                         |
       Catalog Service          Circulation Service
              |                         |
          PostgreSQL               PostgreSQL
              |                         |
            Redis                    Redis
              |                         |
              +------ RabbitMQ --------+
                       события

          Синхронное взаимодействие: gRPC
          Наблюдаемость: slog + OpenTelemetry + Prometheus
```

Схема показывает целевое направление развития. Не все компоненты уже
реализованы или подключены.

### Слои Catalog Service

Внутри сервиса используется разделение ответственности:

-   **HTTP API (`httpapi`)** --- маршруты, обработка HTTP-запросов и
    формирование ответов;
-   **Catalog (`catalog`)** --- доменные типы, интерфейсы репозиториев и
    бизнес-логика;
-   **Memory (`memory`)** --- хранение данных в памяти;
-   **Postgres (`postgres`)** --- реализация хранения данных в
    PostgreSQL.

`main.go` выступает точкой сборки приложения: создаёт зависимости и
передаёт их компонентам. Бизнес-логика зависит от интерфейса
репозитория, а не от конкретного способа хранения данных.

## Требования

Для локальной разработки необходимы:

-   Go версии, указанной в `go.mod` соответствующего модуля;
-   Docker Engine;
-   Docker Compose;
-   Git.

Для ручной работы с PostgreSQL можно использовать `psql` или любой
совместимый клиент.

## Локальный запуск

### 1. Клонировать репозиторий

``` bash
git clone <repository-url>
cd virtual-library
```

### 2. Подготовить конфигурацию

``` bash
cp .env.example .env
```

Заполнить `.env` локальными значениями. Не добавлять этот файл в Git.

### 3. Запустить PostgreSQL

``` bash
docker compose up -d postgres
```

Проверить состояние контейнера:

``` bash
docker compose ps
```

### 4. Запустить Catalog Service

``` bash
cd catalog-service
go mod download
go run ./cmd/catalog
```

Приложение загружает локальные настройки из `../.env` при запуске из
каталога `catalog-service`.

> На текущем этапе команды запуска описывают локальный сценарий
> разработки. По мере добавления миграций и новых сервисов инструкции
> будут расширяться.

## Конфигурация

Локальные переменные задаются в корневом файле `.env`. Шаблон переменных
хранится в `.env.example`.

Текущие параметры:

  Переменная            Назначение
  --------------------- --------------------------------------------
  `APP_PORT`            Порт HTTP-сервера
  `POSTGRES_USER`       Пользователь PostgreSQL
  `POSTGRES_PASSWORD`   Пароль PostgreSQL
  `POSTGRES_DB`         Имя базы данных
  `DATABASE_URL`        Строка подключения приложения к PostgreSQL

Пример шаблона:

``` dotenv
APP_PORT=8080

POSTGRES_USER=your_user
POSTGRES_PASSWORD=your_password
POSTGRES_DB=virtual_library
DATABASE_URL=postgres://your_user:your_password@localhost:5432/virtual_library?sslmode=disable
```

Не храните реальные пароли, токены и другие секреты в репозитории. Для
production-окружений конфигурация должна передаваться безопасным
способом через переменные окружения или секрет-хранилище.

## Работа с базой данных

Локальная PostgreSQL запускается через Docker Compose. Схема базы данных
включает таблицы каталога:

-   `books` --- книги;
-   `authors` --- авторы.

Связь между книгами и авторами реализована внешним ключом
`books.author_id`.

Миграции пока находятся в плане развития. После подключения инструмента
миграций изменения схемы должны оформляться версионируемыми SQL-файлами,
а не только ручными командами.

## Тестирование

Unit-тесты запускаются из каталога соответствующего Go-модуля:

``` bash
cd catalog-service
go test ./...
```

Unit-тесты проверяют поведение отдельных компонентов и могут
использовать in-memory репозиторий или fake-реализации интерфейсов.

Интеграционные тесты с PostgreSQL и другими инфраструктурными
компонентами будут добавлены отдельно. Для них планируется использовать
Testcontainers.

Порядок может уточняться по мере развития проекта.

## Принципы разработки

-   Предпочитать простые решения, соответствующие задачам проекта.
-   Разделять ответственность между HTTP-слоем, бизнес-логикой и
    хранением данных.
-   Определять интерфейсы со стороны потребителя и не создавать
    абстракции без необходимости.
-   Не связывать бизнес-логику с конкретной базой данных или
    инфраструктурным адаптером.
-   Проверять ошибки и корректно обрабатывать граничные случаи.
-   Покрывать бизнес-логику unit-тестами, а интеграции ---
    интеграционными тестами.
-   Не хранить секреты в системе контроля версий.
-   Документировать архитектурные решения и ограничения по мере их
    появления.
