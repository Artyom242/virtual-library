# Virtual Library

Учебный backend-проект виртуальной библиотеки на Go. Проект развивается как система из двух сервисов и предназначен для практического изучения разработки REST API, работы с PostgreSQL, межсервисного взаимодействия, тестирования и эксплуатации backend-приложений.

> **Статус проекта:** в разработке. Основная функциональность `Catalog Service` реализована: CRUD книг и авторов, PostgreSQL-хранилище, транзакционный сценарий создания книги вместе с новым автором, структурированное логирование. `Circulation Service` пока находится на этапе проектирования.

## Цели проекта

Virtual Library — практический проект для разработки backend-системы на Go. Основные цели:

- спроектировать и реализовать несколько взаимодействующих сервисов;
- освоить идиоматичный Go и распространённые подходы к организации backend-приложений;
- реализовать REST API и межсервисное взаимодействие;
- работать с реляционной базой данных, транзакциями и миграциями;
- применять unit- и интеграционные тесты;
- освоить кэширование, асинхронную обработку событий и базовые практики отказоустойчивости;
- добавить наблюдаемость и подготовить приложения к запуску в контейнерах.

Проект ориентирован на обучение практикам, применимым в реальных backend-системах. Инструменты добавляются по мере появления соответствующих задач, а не только ради расширения стека.

## Функциональность

### Catalog Service

Сервис отвечает за каталог библиотеки.

**Реализовано:**

- CRUD книг;
- CRUD авторов;
- связь книги с одним автором;
- PostgreSQL-репозитории на базе `pgxpool`;
- разделение HTTP-обработчиков, бизнес-логики, доменных контрактов и слоя хранения;
- транзакционный сценарий создания книги вместе с новым автором;
- менеджер транзакций;
- структурированное логирование через `log/slog`;
- централизованные прикладные ошибки для формирования единообразных HTTP-ответов.

Точный набор доступных HTTP-маршрутов определяется в `catalog-service/internal/httpapi/router.go`.

**Ещё предстоит:**

- SQL-миграции;
- unit- и интеграционные тесты;
- поиск, фильтрация и дополнительные возможности каталога.

### Circulation Service

Сервис проектируется и будет отвечать за физическое обращение книг в библиотеке:

- учёт зарегистрированных читателей;
- учёт физических экземпляров книг;
- выдача экземпляров, возврат и история выдач;
- контроль доступности экземпляров;
- продление срока выдачи.

Согласованные бизнес-правила:

- одна библиотека, только физические книги;
- у книги может быть несколько физических экземпляров;
- у каждой книги один автор;
- у книги может быть несколько категорий;
- бронирование не предусматривается;
- читатели регистрируются, отдельный статус блокировки пока не нужен;
- одновременно у читателя может находиться не более 5 экземпляров;
- первоначальный срок выдачи — один календарный месяц;
- выдачу можно продлить не более двух раз, каждый раз на один календарный месяц;
- продление возможно только до возврата экземпляра и пока не исчерпан лимит продлений;
- максимальный срок с момента выдачи — три календарных месяца;
- штрафы не входят в первую версию и могут быть добавлены позднее.

### Взаимодействие и инфраструктура

Планируемые возможности:

- gRPC и Protocol Buffers для синхронного межсервисного взаимодействия;
- RabbitMQ для асинхронного обмена событиями;
- Redis для кэширования;
- OpenTelemetry для распределённой трассировки;
- Prometheus для сбора метрик;
- контейнеризация приложений, CI/CD и практики production-развёртывания.

## Архитектура

Репозиторий организован как монорепозиторий с отдельными Go-модулями для сервисов. Каждый сервис отвечает за собственную предметную область и владеет своей моделью хранения данных.

### Целевая логическая схема

```text
                         Клиент
                           |
                      HTTP / REST
                           |
              +------------+------------+
              |                         |
       Catalog Service          Circulation Service
              |                         |
          PostgreSQL               PostgreSQL
              |                         |
              +------ RabbitMQ --------+
                       события

          Синхронное взаимодействие: gRPC
          Наблюдаемость: slog + OpenTelemetry + Prometheus
```

Это целевая схема: не все компоненты уже реализованы или подключены. Сейчас PostgreSQL запускается локально через Docker Compose; Redis, RabbitMQ, gRPC и инструменты наблюдаемости остаются в плане развития.

### Слои Catalog Service

Внутри сервиса используется разделение ответственности:

- **Domain (`domain`)** — доменные типы, интерфейсы репозиториев, прикладные ошибки и контракт транзакционного менеджера;
- **Service (`service`)** — бизнес-логика и сценарии работы с книгами и авторами;
- **HTTP API (`httpapi`)** — маршруты, обработка HTTP-запросов, DTO и формирование ответов;
- **Postgres (`postgres`)** — реализация репозиториев и транзакционного менеджера на PostgreSQL.

`cmd/catalog/main.go` выступает точкой сборки приложения: создаёт инфраструктурные зависимости и передаёт их сервисам и HTTP-обработчикам. Бизнес-логика зависит от контрактов, а не от конкретной реализации PostgreSQL.

## Требования

Для локальной разработки необходимы:

- Go версии, указанной в `go.mod` соответствующего модуля;
- Docker Engine;
- Docker Compose;
- Git.

Для ручной работы с PostgreSQL можно использовать `psql` или любой совместимый клиент.

## Локальный запуск

### 1. Клонировать репозиторий

```bash
git clone <repository-url>
cd virtual-library
```

### 2. Подготовить конфигурацию

```bash
cp .env.example .env
```

Заполнить `.env` локальными значениями. Не добавлять этот файл в Git.

### 3. Запустить PostgreSQL

```bash
docker compose up -d postgres
```

Проверить состояние контейнера:

```bash
docker compose ps
```

### 4. Запустить Catalog Service

```bash
cd catalog-service
go mod download
go run ./cmd/catalog
```

При запуске из каталога `catalog-service` приложение загружает локальные настройки из корневого файла `../.env`.

> Инструкции описывают текущий локальный сценарий разработки. После добавления миграций и второго сервиса порядок запуска будет дополнен.

## Конфигурация

Локальные переменные задаются в корневом файле `.env`. Шаблон переменных хранится в `.env.example`.

| Переменная | Назначение |
|---|---|
| `APP_PORT` | Порт HTTP-сервера |
| `POSTGRES_USER` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL |
| `POSTGRES_DB` | Имя базы данных |
| `DATABASE_URL` | Строка подключения приложения к PostgreSQL |

Пример шаблона:

```dotenv
APP_PORT=8080

POSTGRES_USER=your_user
POSTGRES_PASSWORD=your_password
POSTGRES_DB=virtual_library
DATABASE_URL=postgres://your_user:your_password@localhost:5432/virtual_library?sslmode=disable
```

Не храните реальные пароли, токены и другие секреты в репозитории. Для production-окружений конфигурация должна передаваться безопасным способом через переменные окружения или секрет-хранилище.

## Модель данных

### Catalog Service

Планируемая модель каталога:

- `authors` — авторы;
- `books` — книги, каждая связана с одним автором через `author_id`;
- `categories` — категории книг;
- `book_categories` — таблица связи книг и категорий (многие ко многим).

### Circulation Service

Планируемая модель учёта выдачи:

- `readers` — зарегистрированные читатели;
- `book_copies` — физические экземпляры; одна запись в `books` каталога может соответствовать нескольким экземплярам;
- `loans` — выдачи и история возвратов.

Сервисы владеют отдельными базами данных. `book_copies.catalog_book_id` хранит идентификатор книги из Catalog Service, но не является внешним ключом между базами. Доступность экземпляра определяется наличием активной выдачи; не следует дублировать этот признак отдельным статусом без необходимости.

Это согласованная проектная модель, а не описание уже применённых миграций. SQL-схемы и ограничения будут добавлены при реализации соответствующих сервисов.

## Принципы разработки

- Предпочитать простые решения, соответствующие задачам проекта.
- Разделять ответственность между HTTP-слоем, бизнес-логикой, доменными контрактами и хранением данных.
- Определять интерфейсы со стороны потребителя и не создавать абстракции без необходимости.
- Не связывать бизнес-логику с конкретной базой данных или инфраструктурным адаптером.
- Обрабатывать ошибки явно и не раскрывать клиенту внутренние детали инфраструктуры.
- Использовать транзакции для операций, которые должны выполняться атомарно.
- Покрывать бизнес-логику unit-тестами, а интеграции — интеграционными тестами.
- Не хранить секреты в системе контроля версий.
- Документировать архитектурные решения и ограничения по мере их появления.
